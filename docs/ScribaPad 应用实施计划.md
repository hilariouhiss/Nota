## 1. 本计划的位置与范围

### 1.1 三份文档的权威边界

ScribaPad 的设计基线由三份文档构成，**各自只维护一块信息**，避免同一事实在多处维护而产生分歧：

| 文档                          | 权威范围                                                                 | 不负责                                 |
| ----------------------------- | ------------------------------------------------------------------------ | -------------------------------------- |
| 《软件需求规格说明书》（SRS） | 需求定义、验收标准、需求优先级（M/S/C）                                  | 实施顺序、技术选型、版本划分           |
| 《架构与技术栈设计文档》      | 架构、技术选型、接口协议、**版本划分与各版本覆盖的需求编号**（第 12 章） | 实施顺序、里程碑切片                   |
| **本计划**                    | **实施顺序、里程碑切片、依赖关系、出口标准、风险落位**                   | 需求定义、架构决策、版本划分与需求归属 |

本计划**不重复定义需求**，全部以 `FR-xx` / `PR-xx` / `AC-xx` / `AD-xx` / `ARC-xx` / `R-xx` 引用既有编号。

**需求归属的权威性**：架构文档第 12 章是版本划分与需求归属的**唯一来源**；本计划附录 A 按里程碑重新分组，但**不改变需求所属的版本**。

V0.3 已完成一次回写：本计划第 9 章曾列出的 6 处不一致已全部回写进架构文档 §12，两者现已一致。若今后再现不一致，**以 §12 为准，并回写本计划而非反之**。

### 1.2 范围

覆盖 V1.0 → V2.0 的全部实施工作，共 53 条功能需求（FR-01～FR-53）、10 条性能需求（PR-01～PR-10）、12 条验收标准（AC-01～AC-12）、8 条其他需求（OR-01～OR-08）。**53 条 FR 与 8 条 OR 全部有里程碑归属**（见附录 A）。

> **V0.4 更正**：本节此前只声明覆盖 FR／PR／AC，**未提及 OR**，导致 OR-01～OR-08 长期没有任何里程碑归属（全篇仅 OR-02 被提及一次）。该缺口是在编写 UI 设计规范时发现的——OR-01（快捷键说明）与 OR-03（版本更新说明）的落点正是帮助菜单。现已在附录 A 补入 OR 覆盖，其中 OR-01、OR-03 归入 M5；并新发现 OR-06 属「有需求无功能定义」，列入第 8 章已知缺口。

本计划**不覆盖**：

- 各需求的具体设计（在 SRS 与架构文档中；其中 4 组尚无设计，见第 8 章）
- 步骤级任务分解（每个里程碑开工前单独产出）
- 排期与人力估算（本计划只定义顺序与依赖，不承诺工期）

## 2. 实施原则

排序依据来自本项目已有约束，而非通用偏好：

**P1 每个里程碑必须交付可运行、可验收的软件。**
不以「某一个版本的全部需求做完」作为交付点。V1.0 有约 30 条 FR，若按版本整体推进，在完成前没有任何可演示、可验收的中间状态。因此 V1.0 内部按垂直切片推进（M1–M5），每个切片结束都有可执行的验收动作。

**P2 测试基线先于任何功能开发。**
当前零测试。若先写功能再补测试，后续每个里程碑的验证步骤只能写成「手动点点看」，无法证伪。故 M0 只做工程基线。

**P3 逻辑下沉 Rust 以换取可测性。**
编码检测与转换、会话序列化、搜索匹配、文本缓冲区操作全部实现为 Rust 侧纯函数或纯逻辑模块，用 `cargo test` 覆盖。前端只保留渲染与交互编排。这条原则同时服务架构文档的 ARC-01/ARC-02（渲染归前端、语义归后端）。

**P4 高风险后置，但提前验证。**
架构文档第 12 章刻意把 Tree-sitter + 影子 Rope + 二进制帧（AD-04/05/06/07）推迟到 V1.1，让 V1.0 靠 CodeMirror 6 内置高亮先跑通编辑器。**本计划保留该决策**，但在 V1.0 期间（M2 内）安排一次**技术预研尖刺**：验证二进制帧编解码与影子 Rope 同步的可行性，产出结论而非产品代码。该尖刺不阻塞 V1.0 出口。

**P5 先做能自动验证的部分。**
可由测试覆盖的需求优先于只能人工验收的需求。例如编码转换（AC-06 可自动化）先于主题定制（只能人工看）。

**P6 不擅自补设计。**
架构文档第 5.4 节列出 4 组「尚无组件设计」的需求。它们必须**先补设计再排步骤级计划**，不在本计划中假装已解决（见第 8 章）。

**P7 需求不跨版本拆散。**
同一功能小节（如「设置与主题」FR-37～40、「会话与恢复」FR-41～44）整体落在同一版本内，不因技术理由被切开。这是与架构文档 §12 现有归属的主要分歧点，理由见第 9 章。

## 3. 测试策略

架构文档第 9 章有性能、可靠性、安全、可维护性、可扩展性设计，**唯独没有测试章节**——这是设计基线的空白，本计划补齐。

### 3.1 分层

| 层次             | 工具                                   | 覆盖对象                                                       | 命令                         |
| ---------------- | -------------------------------------- | -------------------------------------------------------------- | ---------------------------- |
| Rust 单元测试    | `cargo test`                           | 编码检测/转换往返、会话序列化、搜索匹配、Rope 编辑、协议编解码 | `cd src-tauri && cargo test` |
| Rust 集成测试    | `cargo test`（`tests/`）               | Tauri command 的输入输出契约                                   | `cd src-tauri && cargo test` |
| 前端单元测试     | Vitest（Vite+ 内置，`vite-plus/test`） | Pinia store、纯函数、协议编解码、路径与格式化逻辑              | `pnpm exec vp test`          |
| 编辑器状态级测试 | Vitest + `@codemirror/state`           | CodeMirror 命令与状态转换（**不测像素**）                      | `pnpm exec vp test`          |
| 端到端           | tauri-driver / WebDriver               | SRS 附录 A 的 12 条验收标准                                    | 待 M6 后引入                 |
| 人工验收         | 检查清单                               | IME 输入、高 DPI、真实中文字体渲染、打印预览                   | 逐里程碑的验收清单           |

### 3.2 关键约定

- **Vitest 不需要单独安装**：Vite+ 1.1.0 已内置并在 `vite-plus/test*` 下再导出 vitest 5.0.3。测试文件从 `vite-plus/test` 引入，不引入 `vitest`。
- **IME 与真实输入法无法自动化**：中文输入法的候选词、组合态、光标行为依赖系统 IME，测试环境无法复现。此类需求**如实写入人工验收清单**，不假装已被自动化覆盖。
- **不做像素级视觉回归**：桌面编辑器收益低、维护成本高。高 DPI（PR-10）与主题（FR-37）用人工验收 + 截图比对。
- **性能需求用可复现的基准脚本**：PR-01～PR-09 需要测量，不做断言式测试（CI 机器性能波动会导致误报），改为基准脚本 + 人工判定，测量方法写入各里程碑的出口标准。

### 3.3 测试的落位

M0 建立 Rust 与前端两条测试链路并各跑通至少一个真实测试。此后**每个里程碑的步骤级计划都遵循 TDD**：先写失败测试 → 确认失败 → 最小实现 → 确认通过 → 提交。

### M0 工程基线

**目标**：让后续每个里程碑都有可运行的验证手段与提交纪律。

**覆盖需求**：无（工程性前置，不消费任何 FR）。

**前置依赖**：无。

**关键任务组**：

1. 前端测试链路：配置 Vitest（自 `vite-plus/test` 引入），添加 `test` 脚本，跑通第一个真实测试
2. Rust 测试链路：在 `src-tauri` 建立 `#[cfg(test)]` 模块与 `tests/` 目录，跑通第一个真实测试
3. CI：在 `vp check` + `pnpm build` 之外加入 `vp test` 与 `cargo test`
4. 提交规范：采用 Conventional Commits；确认 `.gitattributes` 的 LF 策略在 CI 上一致
5. 移除脚手架残留：评估 `greet` 演示命令的去留（当前 `src/App.vue` 调用它）

**出口标准**：

- `pnpm exec vp test` 至少 1 个测试通过
- `cd src-tauri && cargo test` 至少 1 个测试通过
- `pnpm exec vp check` 与 `pnpm build` 仍通过
- CI 配置就位并可运行（本地可复现同样命令）
- 提交规范写入仓库（如 `CONTRIBUTING.md` 或 `.gitmessage`）

**风险**：I-01（Vite+ 的 vitest 集成需实测确认是否需额外配置）。

### M1 应用外壳与编辑内核（V1.0-α）

**目标**：得到能打开、能输入、能撤销的最小编辑器——第一个可人工验收的产物。

**覆盖需求**：FR-01（快速启动）、FR-02（快速退出）、FR-12（基础编辑操作）、FR-14（列编辑）、FR-18（括号匹配）、FR-19（当前行高亮）、FR-20（行号显示）；UI-01（主窗口结构）、UI-06（状态栏）。

**说明**：FR-18、FR-19 使用 CodeMirror 6 内置能力（`bracketMatching()`、`highlightActiveLine()`），**不依赖 Tree-sitter**，因此归入 V1.0 而非 V1.1。

**本里程碑不含语法高亮**：FR-16 归属 V1.1（M6），V1.0 全阶段为纯文本编辑体验。因此 M1 的 CodeMirror 集成**不得引入 `@codemirror/lang-*` 语言包**——语言高亮统一由 M6 的 Tree-sitter 服务提供，提前引入会造成两套高亮机制并存，并在 M6 时需要拆除。

**前置依赖**：M0。

**关键任务组**：

1. 引入依赖：CodeMirror 6 族（`@codemirror/state`、`view`、`commands`）、Pinia、VueUse、`@vicons/fluent`，以及 Naive UI 的 `n-icon`（**M1 只需要 NIcon 这一个组件**——本里程碑无对话框，不要整套引入）
2. 设计令牌模块：`ThemeTokens` 类型 + 内置浅/深两套值，以及三个纯函数 `tokensToCssVars` / `tokensToEditorTheme` / `tokensToNaiveOverrides`（UI 设计规范 §4.1）
3. **中文字宽验证**：确认中日韩字符是否正好占 2 个拉丁字符宽。这是 M1 的第一件事，也是 UI 设计规范 §9.1 的第 1 项待验证——它决定 `--sp-font-mono` 的取值（Consolas 的中文回退到 Microsoft YaHei），并且是列编辑对齐的前提
4. 应用外壳布局：菜单栏、工具栏、标签栏（先单标签）、编辑区、底部面板壳、状态栏（UI 设计规范 §3.1）
5. CodeMirror 6 集成：挂载、基础编辑、行号、撤销/重做、括号匹配、当前行高亮，主题经 `EditorThemeBridge` 由令牌生成
6. 列编辑：`rectangularSelection` 与 `crosshairCursor` 扩展
7. Pinia store 骨架：`documents`（文档集合）、`activeTab`
8. 窗口配置（UI 设计规范 §8.1、§8.2）：默认 1200×800、最小 640×400、标题格式 `文件名 — ScribaPad`，并把 `tauri.conf.json` 的窗口 `backgroundColor` 设为上次主题的编辑区底色（浅 `#ffffff` / 深 `#1c1c1c`），由 Rust 侧创建窗口时读配置决定，以消除深色主题用户的启动闪白

**出口标准**：

- `pnpm dev` 启动后编辑区可输入、删除、撤销、重做
- 行号显示正确且与内容对齐；状态栏显示行列号
- 括号匹配与当前行高亮可开关
- **AC-01**：冷启动 ≤ 1.5 秒、热启动 ≤ 0.5 秒（PR-01/PR-02，用可复现脚本测量，人工判定）
- **PR-08**：空闲内存占用记录基线值（具体阈值由后续测试确定）
- 编辑器命令与状态转换有状态级测试覆盖

**风险**：I-02（编辑器与 IME 行为无法自动化，需在 M0 就把 `EditorState` 级测试跑通，否则本里程碑退化为纯手工验证）。

### M2 文件 I/O 与编码（V1.0-β）

**目标**：真正能打开磁盘上的中文文件、按原编码保存回去。

**覆盖需求**：FR-04（新建）、FR-05（打开）、FR-06（保存与另存）、FR-07（最近文件）、FR-26（编码识别）、FR-27（编码转换）、FR-28（BOM 控制）、FR-29（换行符识别）、FR-30（换行符转换）。

**前置依赖**：M1。

**关键任务组**：

1. Rust 侧引入 `tauri-plugin-fs`、`tauri-plugin-dialog`，并在 `capabilities/default.json` 配置权限
2. Rust 侧 command：`open_file`、`save_file`、`detect_encoding`、`convert_encoding`（接口见架构文档 §6.2）
3. 编码实现：`encoding_rs` + `chardetng`（架构文档 §4.2.7）
4. 换行符识别与转换（CRLF/LF/CR）
5. 前端接入：打开/保存对话框、最近文件列表、状态栏显示编码与换行符
6. **技术预研尖刺（P4）**：验证二进制帧编解码与影子 Rope 同步可行性，产出结论文档，不产出产品代码

**出口标准**：

- **AC-02**：UTF-8、GBK、ANSI 三种中文文件打开后无乱码
- **AC-06**：UTF-8 ↔ GBK 互转内容正确（`cargo test` 覆盖往返一致性）
- **AC-07**：CRLF ↔ LF 互转正常（同样用往返测试覆盖）
- **PR-03**：打开 10MB 文本 ≤ 1 秒
- 编码检测失败时提供手动选择（SRS 2.5 已承认检测不可能 100% 准确）

**风险**：R-07 大文件内存压力初现。本里程碑只要求正确性，不要求 100MB 级性能（那是 M10）。

### M3 多标签、文件监视、会话与崩溃恢复（V1.0-γ）

**目标**：同时编辑多个文件，感知外部修改，重启后恢复现场，崩溃后不丢内容。

**覆盖需求**：FR-08（文件变更监视）、FR-09（多标签打开）、FR-10（标签切换与关闭）、FR-11（标签拖拽排序）、FR-41（会话恢复）、FR-42（崩溃恢复）、FR-43（自动保存）。

**说明**：FR-43 自架构文档 §12 的 V1.1 前移至此，以保持「会话与恢复」功能小节完整（D-3 已于 V0.3 回写 §12）。

**前置依赖**：M2（需要文件读写才能验证恢复）。

**关键任务组**：

1. TabBar 组件：多标签、切换、关闭、拖拽排序、未保存标记
2. 文件变更监视：外部修改时提示重新加载，不静默覆盖用户修改（FR-08）
3. 会话持久化：会话文件（打开文件、光标位置、标签顺序），格式见架构文档 §7.1
4. 自动保存与备份：定时写入备份文件，崩溃后提供恢复提示
5. Rust 侧 atomic write（REL-03：临时文件 + 原子替换）

**出口标准**：

- **AC-03**：同时打开 10 个以上文件，切换无明显延迟（PR-06）
- **AC-08**：强制结束进程后重启，可恢复未保存内容
- 外部修改文件时给出提示而非静默覆盖
- 会话与备份的序列化有 `cargo test` 覆盖
- 会话文件格式带版本号字段（缓解 I-03）

**风险**：I-03（会话/备份格式一旦确定就难以更改，且需同时满足 DD-02 便携模式存程序目录）。**该格式决策必须在 M3 开工前完成**（见第 6 章）。

---

### M4 查找替换（V1.0-δ）

**目标**：当前文件内的查找、正则查找与替换。

**覆盖需求**：FR-21（普通查找）、FR-22（正则查找）、FR-23（替换）。

**说明**：FR-21～23 属单文件能力，且 SRS 优先级为 M，自架构文档 §12 的 V1.2 前移至此（D-2 已于 V0.3 回写 §12）。该前移是 AC-12（普通用户 5 分钟内完成打开、编辑、保存、**查找替换**）能在 V1.0 出口验收的前提。

**前置依赖**：M3。

## 5. 依赖关系

```text
M0 工程基线
 │
 └─► M1 应用外壳与编辑内核 ──► M2 文件 I/O 与编码 ──► M3 多标签/文件监视/会话恢复
```

## 9. 与架构文档 §12 的需求归属（已回写）

本计划初稿曾与架构文档 §12 在 6 处不一致。**V0.3 已按下表逐条回写 §12 的「覆盖需求」列**，三份文档现已一致；下表保留为决策记录，「回写后归属」即当前 §12 与本计划附录 A 的共同归属。

| 编号 | 需求                                       | §12 原归属         | 回写后归属                     | 理由                                                                                                                                                            |
| ---- | ------------------------------------------ | ------------------ | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-1  | FR-18（括号匹配）、FR-19（当前行高亮）     | V1.1               | **V1.0 / M1**                  | 两者均由 CodeMirror 6 内置能力提供（`bracketMatching()`、`highlightActiveLine()`），**不依赖 Tree-sitter**。放在 V1.1 会让 V1.0 缺两个 M/S 级编辑辅助能力。     |

| D-3  | FR-43（自动保存）、FR-44（备份管理）       | V1.1               | **V1.0**（FR-43→M3、FR-44→M5） | §12 把「会话与恢复」小节切成两半（FR-41～42 在 V1.0、FR-43～44 在 V1.1）。二者共享同一套存储与备份机制，切开会导致该机制在两处各写一遍。                        |
| D-4  | FR-39（快捷键设置）、FR-40（配置导入导出） | V1.1               | **V1.0 / M5**                  | 同理，§12 把「设置与主题」小节切成两半（FR-37～38 在 V1.0、FR-39～40 在 V1.1）。四者共享同一份配置文件读写实现，拆开无技术收益。                                |
| D-5  | FR-08（文件变更监视）                      | **未列入任何版本** | **V1.0 / M3**                  | §12 的覆盖需求列遗漏了该需求。它依赖文件状态跟踪，与多标签、会话同属 M3 的责任范围。                                                                            |

**关于 M 级需求覆盖范围的确认**：架构文档 §12 的需求归属与 SRS 的 M/S/C 优先级体系并不一一对应，最典型的是 FR-16（语法高亮）——SRS 标为 **M（必须实现）**，但受技术依赖约束落在 V1.1。

V0.3 已确认：**FR-16 留在 V1.1**，即 V1.0 **不要求**覆盖全部 M 级需求。其结果是 V1.0 全阶段为**纯文本编辑体验**，不含语法高亮。

该决定的可行性已核验：**SRS 附录 A 的 AC-01～AC-12 没有任何一条依赖语法高亮**，因此 V1.0 仍可通过自身的全部验收标准。相应地，M1 明确禁止提前引入 `@codemirror/lang-*` 语言包，避免与 M6 的 Tree-sitter 高亮形成两套并存机制。
